    #Task 1

❓ Что произойдет, если никто не нажмет «Одобрить» (Approve), и как вы с этим справились?

Ответ:
Если оставить шаг input (ручное подтверждение) без контроля, пайплайн зависнет в режиме ожидания бессрочно. Это 
заблокирует исполнитель (executor) Jenkins, из-за чего другие сборки и проекты встанут в очередь, а ресурсы сервера 
будут расходоваться впустую.
Как мы с этим справились:
Мы изолировали шаг ручного подтверждения, добавив на этапе Approve Deployment локальный блок options { timeout(time: 
15, unit: 'MINUTES') }.
Если в течение 15 минут человек не зайдет в интерфейс Jenkins и не нажмет кнопку «Апрув», этот конкретный этап 
автоматически прервется по таймауту. При этом сборка перейдет в статус ABORTED (Отменена), освобождая исполнитель для 
других задач в кластере.

❓ Почему очистка (Cleanup) должна быть в блоке post { always { ... } }, а не просто отдельным финальным этапом (stage)?

Ответ:
Если вынести очистку среды (удаление временного pre-prod контейнера) в обычный финальный этап (stage('Cleanup')), 
система станет крайне уязвимой:
1. Если пайплайн упадет из-за ошибки на любом из предыдущих этапов (например, завалятся тесты на Test Pre-Prod или 
2. упадет билд), Jenkins сразу прервет выполнение и пропустит все последующие шаги. Финальный этап очистки просто не запустится.
2. В результате на сервере останутся «мусорные» запущенные контейнеры и занятые порты, что приведет к конфликтам при следующих запусках.
   Почему блок post { always { } } — это правильно:
   Блок post со спецификатором always является частью декларативного синтаксиса Jenkins, которая работает на уровне ядра
3. пайплайна. Инструкции внутри always гарантированно выполнятся в любом случае:
   • При успешном завершении (SUCCESS).
   • При падении любой из предыдущих стадий (FAILURE).
   • При отмене сборки человеком или по таймауту (ABORTED).
   Это обеспечивает стопроцентную очистку инфраструктуры и освобождение портов сервера при любом исходе сборки.

    #Task 2

❓ Сколько контейнеров в итоге оказалось в поде (капсуле) и откуда взялся лишний?

Ответ:
В итоге в поде оказалось 3 контейнера (что наглядно подтверждает статус 3/3 READY в выводе команды kubectl get pods).
• Два контейнера мы описали в YAML-манифесте пайплайна сами: это builder (для сборки) и tester (для тестов).
• Третий («лишний») контейнер называется jnlp (в старых версиях) или inbound-agent. Его автоматически внедряет 
(инжектирует) сам плагин Jenkins Kubernetes. Этот контейнер жизненно необходим: он устанавливает двустороннюю связь 
между сервером Jenkins (Master) и запущенным подом-агентом, передает команды внутрь нашего пода и возвращает логи шагов
обратно в интерфейс Jenkins.

❓ Зачем контейнерам в манифесте предоставляются инструкции command: ['cat'] и tty: true (или command: ["sleep"])?

Ответ:
По умолчанию официальные Docker-образы Linux (такие как alpine, ubuntu или debian) созданы для интерактивного режима. 
Если запустить их в Kubernetes без указания долгоживущей команды, контейнер моментально выполнит свою основную задачу 
(которой у чистого Linux нет), решит, что ему больше нечего делать, и завершит работу. Под перейдет в статус Completed
и удалится еще до того, как Jenkins успеет передать ему команды пайплайна.
Инструкции command: ['cat'] (или command: ["sleep", "99d"]) вместе с параметром tty: true принудительно запускают 
бесконечный фоновый процесс, который "обманывает" Kubernetes и держит контейнер в активном состоянии Running. Контейнер 
ёпостоянно ожидает ввода данных, что позволяет Jenkins в любой момент заходить внутрь него и выполнять шаги сборки.

❓ Что делать, если сборка пайплайна не удалась, а под-агент в Kubernetes уже автоматически удален? Как посмотреть логи?

Ответ:
Так как под-агент удаляется сразу после окончания работы пайплайна (благодаря логике работы плагина), стандартная 
команда kubectl logs для удаленного пода больше не сработает. Чтобы разобраться в причинах сбоя, используют следующие подходы:
1. Консольный вывод Jenkins (Console Output): Это главный источник информации. Jenkins успевает выкачать абсолютно все 
логи (stdout/stderr) из подов в режиме реального времени до того, как они будут уничтожены кластером. Любая ошибка 
компиляции, линтера или упавшего скрипта будет зафиксирована в логе сборки Jenkins.
2. Системные логи Jenkins Master: Ошибки создания самого пода (например, если в кластере не хватило ресурсов CPU/RAM 
или указан несуществующий образ) логируются в разделе Dashboard -> Manage Jenkins -> System Log.
3. Использование внешних систем логирования (ELK Stack / EFK / Grafana Loki): Если в кластере настроен сбор логов, то 
логи всех контейнеров (даже удаленных) автоматически улетают в централизованное хранилище, где их можно найти по 
5. имени пода или лейблу some-label: jenkins-agent.
Временное отключение удаления пода для отладки: В настройках плагина Kubernetes внутри Jenkins можно временно 
увеличить время жизни пода после сбоя (Retention Strategy), чтобы успеть зайти внутрь него через kubectl exec и провести
диагностику вручную.
