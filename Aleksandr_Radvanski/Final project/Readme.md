## 2. Pipeline: high-level design

The flow from a code change to a running version:

1. A developer pushes or opens a Pull Request in the `app-repo` repository (branches `main` and `develop`).
2. GitHub Actions (CI) runs: code checks (hadolint, yamllint), unit tests, image build, integration and functional tests.
3. For the `main` branch only: the image is published to GitHub Container Registry (GHCR) with the tags `<sha7>` and `latest`.
4. For `main` only: the `deploy` job connects to the Hetzner server over SSH and runs `/opt/wiki/deploy.sh deploy <sha7>` (the script files are stored in `pipeline-repo`).
5. On the server, `deploy.sh` backs up the database, starts the inactive color (blue or green) with the new image and waits for the `/healthz` health check.
6. If the health check passes, nginx switches to the new color (reload without dropping connections); the old color is stopped but kept for rollback.
7. If the health check fails, the new container is stopped and traffic stays on the old version (automatic rollback).
8. At each stage a Telegram bot sends notifications: deploy start, result (success or failure), CI failure, manual rollback.

## 3. Technologies used

### Orchestration

GitHub Actions (hosted runner `ubuntu-latest`). The `ci-cd.yml` workflow consists of the jobs `lint`, `build-test` and `deploy`; the `rollback.yml` workflow runs a manual rollback.

### Automation tools

- Bash: `deploy.sh` (deploy, rollback, status) and the test scripts `tests/unit.sh`, `tests/integration.sh`.
- Docker and Docker Compose: image build, running two services (blue, green) and nginx.
- nginx: reverse proxy; the `upstream.conf` file is generated by the script and points to the active color.
- GHCR: image storage.
- curl and the Telegram Bot API: notifications.

### CI implementation

- **Trigger type:** GitHub webhook (`push` and `pull_request` events on the `main` and `develop` branches), plus manual `workflow_dispatch`.
- **Code checks:** hadolint (Dockerfile), yamllint (configuration and workflows).
- **Unit tests:** `tests/unit.sh` checks the application configuration (SQLite, data path, port).
- **Build:** `docker build`; the image is tested before publishing.
- **Integration tests:** `tests/integration.sh` starts a container, checks `/healthz` and the presence of the `db.sqlite` file.
- **Functional test:** a `GET /` request must return status 200.
- **Publishing:** for `main` only, tags `<sha7>` and `latest`.
- **Trivy image scanning is excluded from the pipeline:** in March 2026 a supply-chain security incident affected the `aquasecurity/trivy-action` action, so using a third-party action was judged an unjustified risk.
- **Branching strategy:** in `app-repo` the branches are `main` (production, triggers a deploy), `develop` (integration, CI only) and `feature/*` (tasks, merged into `develop` through a Pull Request); in `pipeline-repo` the branches are `main` and `feature/*` through a Pull Request. The description is in the `README.md` of each repository.

### Deployment sequences

**New deployment (first run):**

1. There is no active color yet, so `blue` is chosen.
2. The image is pulled from GHCR, the `wiki-blue` container starts, and the `wiki_wikidata` volume is created automatically.
3. The script waits for the `healthy` state (up to 40 checks at 3-second intervals, about 2 minutes).
4. `upstream.conf` is generated, nginx starts, and `blue` is written to `state/active`.
5. The initial Wiki.js setup is done in the browser (administrator, Site URL).

**Update deployment (zero downtime, data preserved):**

1. A backup copy of `db.sqlite` goes to `/opt/wiki/backups/`.
2. The inactive color is chosen, and the new image tag is written to `state/<color>.tag`.
3. The image is pulled and the new container starts next to the old one; both use the same volume with the data.
4. The script waits for the new container's health check.
5. nginx is switched (`nginx -s reload`) and `state/active` is updated.
6. The old container is stopped (its image stays on the server for a quick rollback).

### Rollback strategy

**Automatic rollback:**

- Trigger: the new container did not reach the `healthy` state within 2 minutes.
- What happens: the new container is stopped, the image tag in `state/` is restored to its previous value, nginx is not switched, and users keep working on the old version. The `deploy` job ends with an error, and a failure notification arrives in Telegram.

**Manual rollback:**

- Start: the `rollback` workflow on the Actions tab (Run workflow button), or the command `deploy.sh rollback` on the server.
- What happens: the previous color starts with its saved tag, the script waits for `healthy`, switches nginx and stops the current color. If the previous version is unhealthy, the rollback is aborted and traffic stays on the current one.

**Implementation details:**

- State is stored in the files `state/active`, `state/blue.tag`, `state/green.tag`.
- Container health check: `wget http://127.0.0.1:3000/healthz`. The address `127.0.0.1` is deliberate: inside an Alpine container `localhost` resolves to IPv6, while the application listens only on IPv4.
- User data lives in the shared volume, so it is lost neither on update nor on rollback; a database backup is also made before every update.
- Automatic rollback demo: the health check is deliberately broken on the server by replacing the path `/healthz` with `/broken`, then a deploy is started.

### Notifications

The Telegram bot sends messages about the deploy start, its result, CI failures and the result of a manual rollback. The token and chat ID are stored in GitHub Secrets (`TELEGRAM_TOKEN`, `TELEGRAM_CHAT_ID`).

### Pipeline performance testing

Stage times were measured from GitHub Actions data (GitHub CLI, `gh api .../jobs`) for successful runs.

| Stage | Samples | Average | Minimum | Maximum |
| --- | --- | --- | --- | --- |
| lint | 9 | 10 s | 8 s | 14 s |
| build-test | 7 | 43 s | 35 s | 56 s |
| deploy | 4 | 18 s | 17 s | 19 s |

Full duration of a successful run (start to finish, 7 runs): about 65 seconds on average, ranging from 23 to 88 seconds. The most stable stage is deploy (spread of 2 seconds); the largest spread is in build and tests (21 seconds), which is explained by the load on cloud runners.
